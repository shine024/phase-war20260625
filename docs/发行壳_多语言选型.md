## 二、方案对比

### 方案 A：Godot CSV translation 工作流（引擎原生）

- 机制：字符串提取 → `locale.csv`（key,en,zh,…）→ Import 为 Translation 资源 → 显示点包 `tr("KEY")` → `TranslationServer.set_locale()` 切换。
- 优点：引擎原生、编辑器内可翻译导出、复数/上下文支持、切语言零重启。
- 缺点：**2,259+ 处 UI 字符串要逐处改造成 key**——一次性工程量大，且 key 化后中文可读性下降（调试需对照表）。
- 适配成本估算：提取工具（正则扫中文字面量生成初版 CSV）≈ 2~3 天；逐面板人工校 key/上下文 ≈ 15~25 天（2,259 行 × 复核）；**合计 ≈ 4~6 周**（1 人）。

### 方案 B：运行时替换（数据驱动）

- 机制：不动引擎翻译层；数据层每条目带 `name_en`/`desc_en`，UI 层加 `L10n.t(key)` 薄封装按当前语言取字段；UI 硬编码文案维持中文、仅对**主干界面**（标题/底栏/结算/教程）出英文版常量表。
- 优点：数据层改动小（249 改造已有 name_en，铺到卡牌/符文即可）；主干 UI 可控地先英文化；与现有 data-as-code 架构同构。
- 缺点：非引擎标准路径，长尾 UI 文案覆盖慢；描述类长文本（词条/风味）翻译量仍大。
- 适配成本估算：数据层铺字段 + L10n 薄封装 ≈ 1 周；主干 UI 英文化 ≈ 1~2 周；长尾渐进。**主干可玩英文版 ≈ 2~3 周**。

### 结论与推荐

**推荐 B 为主、A 局部补**：
1. 第一期（发行壳批次内）：方案 B——数据层 name_en 已有基础，主干 UI 常量表英文化，
   商店页可如实标注"英文界面支持"。
2. 第二期（上线后）：若英文区销量成立，再做方案 A 全量 CSV 化（届时 B 的薄封装可作
   tr() 的取数后端，前期投入不报废）。
3. 纪律：新代码不加深债务——新增玩家可见文案尽量集中于数据层字段（天然双语位），
   UI 一次性提示文案集中到常量表文件，禁止散落新硬编码。
