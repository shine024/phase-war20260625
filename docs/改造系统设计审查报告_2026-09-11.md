## 1. 系统架构概览

| 层 | 核心组件 | 职责 |
|---|---|---|
| **数据注册** | `scripts/systems/modification_registry.gd` | 10个兵种模块类的统一注册、查询、效果应用 |
| **模块定义** | `data/modification_modules/*_mods.gd`（10个文件） | 140+改造模块的静态数据（effects, era_band, conflict_group等） |
| **战力计算** | `managers/evolution/mod_manager.gd` | 改造消耗公式、战力档位门槛、已装数量查询 |
| **生命周期** | `managers/blueprint_manager.gd` | 安装/升级的持久化写入 + 蓝图消耗 |
| **UI面板** | `scenes/ui/modification_panel.gd`（2350行） | 三栏布局：名册 → 改造库 → 单位详情 + 底部操作台 |
| **消耗品化** | `managers/intel_item_bag.gd` + `data/blueprint_definitions.gd` | 图纸库存管理，消费型蓝图 |

## 2. 当前设计亮点 ✅

### 2.1 v10 改造二分法（机制 vs 数值）

**设计原则**：
- **机制改造（mechanic）**：改变单位"怎么打"（行为规则/触发条件/新能力）
- **交换比改造（ratio）**：改变"打得多划算"（数值效率）

**实现方式**：
- `MECHANIC_EFFECT_KEYS` 表覆盖 ~40+ 键，自动分类
- UI 用橙色 `[机制]` / 灰色 `[数值]` 标签区分，玩家直观感知"战法 vs 变强"
- `get_mod_class_display()` 给情报面板同步复用

**典型机制改造**：
```
反伤/拦截：reactive_armor, intercept_system, missile_intercept
成长爆发：combo_system, rage_system
叠层 debuff：armor_break, crit_mark
标记系统：target_marking, mark_vuln
真实伤害：true_damage, siege_bonus_pct
DOT弹头：chem_chance, burn_chance, nano_infect
亡语/濒死：death_heal, ifak_revive
溅射：splash_radius, splash_damage
跨维度武器：grant_slot
周期脉冲（v27 mythic）：vanguard_repair, aegis_pulse_cd, gravity_pulse_cd
```

### 2.2 v22 四通道数值体系

| 通道 | 语法 | 语义 | 示例 |
|---|---|---|---|
| **set（替换）** | `<stat>_set` | 直接替换基础值 | `attack_armor_set = 272` |
| **flat（固定）** | `<stat>` (int) | 平加，攻击/HP族随时代缩放 | `attack_light = 8` |
| **pct（百分比）** | `<stat>_pct` | 百分比叠加 | `defense_armor_pct = 0.08` |
| **混合** | flat + pct 并存 | 同条目多维增益 | 倾斜装甲 |

**时代适配双轨**：
- **硬门**：`era_band = [min, max]`（0一战~4近未来），装配过滤 + 安装守卫
- **软缩放**：攻击/HP族 int flat 值随宿主时代缩放（×1.0 ~ ×6.3）

**缩放表来源**（卡池中位数推导，与 v6.8"时代膨胀烘进卡表原值"决策一致）：
```
atk 归一：39 / 71 / 105 / 205 / 232  → 缩放 1.0 / 1.8 / 2.7 / 5.3 / 6.0
hp 归一：175 / 409 / 572 / 900 / 1100 → 缩放 1.0 / 2.3 / 3.3 / 5.1 / 6.3
```

### 2.3 战力档位门槛（刚性门禁）

`ModManager.get_min_power_tier_for_mod()` 按 rarity 派生门槛，无需改 140+ 定义数据：

| 稀有度 | 最低档位 |
|---|---|
| common | GRUNT（无门槛） |
| uncommon | VETERAN |
| rare | ELITE |
| epic | CHAMPION |
| legendary / mythic | OVERLORD |

面板显示："✗需CHAMPION（当前ELITE）"，明确告知玩家卡在哪里。

### 2.4 消耗品化蓝图（v26.x）

- 数据源从「库存 > 0」改为「见过集合」——消耗光最后一张图纸后模块仍留在列表（灰显"图纸不足"）
- 旧体系下 consume_item 零调用、库存只增不减，inventory 回填已覆盖全部历史获取
- 安装按钮 tooltip 就地说明缺什么、去哪拿（制造舱补给出口）

### 2.5 v27 改造升级体系

- 已装改造支持 Lv1 → Lv2 → Lv3 三级升级
- 升级按钮在右栏已装列表 + 底部操作台双入口
- 费用同源：`preview_upgrade_cost()` 与真实扣款一致
- 升级条件：`can_upgrade` 字段 + 当前 level < 3

### 2.6 效果模拟抽屉（v1.5）

**三栏布局**：
1. **完整效果**：复用 `_format_effects_for_display()`，兼容 effects / level_effects / grant_slot
2. **属性对比**：before → after + delta（green/up, red/down），机制类改造显示"无直接数值变化"
3. **战力预估**：当前战力 / 装上后 / 变化量 / 槽位占用

**关键修复**：
- 原 `after = before × power_mult` 严重虚高（power_mult 是稀有度权重，非战力增益倍率，1.35 会对 3000 战力卡显示 +1050）
- 改为克隆实例卡 + 追加候选改造，走与真实安装完全相同的 `build_stats → combat_power` 路径

## 3. 发现的问题与风险 🔍

### 3.1 改造数量与测试覆盖不匹配

**现象**：
```gdscript
// __init__.gd 注释: "包含全部202个改造模块定义"
// modification_registry.gd 注释: "管理所有140+个改造模块"
// universal_mods.gd 仅预加载了 GEN_01~GEN_13（13个通用）
```

**风险**：202 vs 140+ 不一致，v8批次5新增的3个相位共鸣改造（GEN_11~13）是否计入202？需确认实际总数。

**影响**：`tests/unit/data/modification_modules_test.gd` 的数量锁断言可能失败或掩盖新问题。

---

### 3.2 era_band 时代的"半透明"语义

**现状**：
- 硬门过滤只拦"超带不可装"
- **已装的超带改造继续生效（不追溯）**

**设计意图**：清晰（不破坏老存档），但玩家可能在面板看到"已装 XXX已过期但仍生效"的困惑。

**建议**：已装超带条目加时效标注（如"已归档·仍生效"badge）

---

### 3.3 战力档位门槛的刚性边界 case

**问题**：
- `can_install_by_power_tier` 是硬性门
- 战力计算依赖 `BlueprintManager.estimate_power_score`，对无战斗历史的卡返回 0
- **边界 case**：新获得的卡（有实例但还未战斗过）战力为 0 → 任何 epic+ 改造都装不上

**建议**：首次获得卡在 install 时给一个"最低战力评估"（用模板基础战力估算，min=1档）

---

### 3.4 _guess_combat_kind 的脆弱性

**现状**（`universal_mods.gd:184-230`）：
```gdscript
if card_id.begins_with("ww1_arm_rolls") or card_id.begins_with("ww1_lanchest") ...
# 单卡 miss → 归为 LIGHT(0) → 错过大量通用改造
```

**维护成本**：随新卡增加，前缀列表持续膨胀。

**建议**：改由 `DefaultCards.get_card_by_id(card_id).combat_kind` 直接读取，而非猜测。

---

### 3.5 改造冲突组的数据一致性

**现状**：
- `conflict_group` 在模块定义里硬编码
- 跨模块检查依赖 `check_conflict(card, mod_id)` 遍历 `installed_modifications`
- 如果新改造忘了写 `conflict_group`，冲突检查静默跳过（返回 false）

**建议**：`register_all()` 末尾做一次完整性校验（同兵种内同名 conflict_group 应有 ≥2 个条目）

---

### 3.6 效果模拟抽屉的战力预估竞态

**现状**：
- `_open_sim_drawer()` 依赖 `_cached_card_power`（单次刷新缓存）
- 若用户在不同选卡间快速切换，缓存可能过期

**建议**：抽屉打开时重新计算一次（加脏标记），或在 `_on_card_selected` 时强制刷新缓存

---

### 3.7 v7.5 move_speed 重定向的隐性契约

**历史背景**：
- `move_speed` 从"移动速度"语义改为"部署延迟百分比"
- 系数 0.005 → 0.02（×4）并修正符号（`+=` → `-=`）
- 所有现存改造的 `move_speed` 值都是**负数**（减速 = 减延迟）

**风险**：新设计者添加改造时容易误用正数 → 变成"增加延迟"的反效果

**建议**：
1. 在 `MECHANIC_EFFECT_KEYS` 旁边加警告注释
2. 或把 key 改名 `deploy_delay_bonus`（旧值自动翻转迁移）

---

### 3.8 改造面板代码体量

**现状**：`modification_panel.gd` 2350 行，是单体面板中最大的文件之一。

**风险**：
- 新功能添加容易耦合
- 单元测试困难
- 新人阅读成本高

**建议**：中期拆分为：
- `mod_panel_list_view.gd`（名册 + 改造库渲染）
- `mod_panel_detail_view.gd`（右栏单位面板 + 操作台）
- `mod_panel_sim_drawer.gd`（效果模拟抽屉）
- 主面板只保留状态管理和事件分发

## 4. 数据流一致性检查

| 路径 | 状态 | 备注 |
|---|---|---|
| 蓝图消费 → 库存扣减 | ✅ | `IntelItemBag.has_item` + `consume_item` |
| 纳米消耗 → 余额扣减 | ✅ | `BasicResourceManager` |
| 安装 → `blueprint_mods` 持久化 | ✅ | `instance_id` 作为 key |
| 升级 → 同 key 覆盖 level 字段 | ✅ | `_on_upgrade_pressed` 写回 |

| 战力档位门槛 → 面板显示 | ✅ | `_cached_card_power` + `can_install_by_power_tier` |
| 改造冲突 → 安装拦截 | ✅ | `can_install_modification` 返回 reason |
| 效果模拟 → 战力预估路径 | ✅ | 克隆实例卡走真实 build_stats |
| v22 set 通道守卫 → 更优才生效 | ✅ | 替换值 ≤ 当前值时不覆盖 |

#### 5.4 首次获得卡的战力估算
**文件**：`managers/evolution/mod_manager.gd` 或 `modification_panel.gd`

**目标**：对无战斗历史的卡用模板基础战力估算

```gdscript
# _compute_card_power_once 增加兜底
func _compute_card_power_once() -> float:
    if selected_card == null or BlueprintManager == null:
        return 0.0
    var key = selected_card.instance_id if not selected_card.instance_id.is_empty() else selected_card.card_id
    if key.is_empty():
        return 0.0
    var power = EvolutionHelpers.estimate_power_score(key, BlueprintManager)
    if power <= 0:
        # 兜底：用模板基础战力（不含改造加成）
        var dc = load("res://data/default_cards.gd")
        var tpl = dc.get_card_by_id(selected_card.card_id)
        if tpl != null:
            power = _template_base_power(tpl)
    return power
```

#### 5.5 conflict_group 完整性校验
**文件**：`scripts/systems/modification_registry.gd` `register_all()` 末尾

**目标**：扫描同兵种内同名 conflict_group 应有 ≥2 个条目

```gdscript
static func _validate_conflict_groups() -> void:
    var group_counts: Dictionary = {}
    for type_key in _cache.keys():
        for mod_id in _cache[type_key].keys():
            var data = _cache[type_key][mod_id]
            var group = String(data.get("conflict_group", ""))
            if not group.is_empty():
                if not group_counts.has(group):
                    group_counts[group] = {"count": 0, "examples": []}
                group_counts[group]["count"] += 1
                if group_counts[group]["examples"].size() < 2:
                    group_counts[group]["examples"].append(mod_id)

    for group in group_counts.keys():
        if group_counts[group]["count"] < 2:
            push_warning("[ModificationRegistry] conflict_group '%s' 仅有 %d 个条目，冲突检查无效" % [group, group_counts[group]["count"]])
```
