# P0 运行时战斗帧率优化计划

## 目标
消除战斗密集交火时的 3 个 per-frame / per-hit GC 分配热点。改动集中、风险可控、向项目已有的优化模式（v7.3 手写动画、对象池）对齐。

## 三个优化点

### 优化 1：批处理 `_sync_multimesh_layers` buckets 成员化复用
**问题**：三个批处理文件每物理帧新建 1 Dictionary + 4~5 个 Array 做 weapon_type 分桶（60fps × 3 文件 = 每帧 ~3 dict + ~13 array 分配）。

**改法**（建议 A，最小改动）：把 `buckets` 提升为成员变量，`_ready()` 里按 `_BATCH_WEAPON_TYPES` 预分配空 Array，`_sync_multimesh_layers` 开头改为 `clear()` 复用（保留内部 buffer 容量，下帧 append 不 realloc）。

**涉及文件**（3 个，每个改 ~6 行）：
- `managers/battle/simple_player_projectile_batch.gd` — 加 `var _buckets` 成员；`_ready` 末尾初始化；`_sync_multimesh_layers`（L121-123）改 clear 复用，后续 `buckets` 引用改 `_buckets`
- `managers/battle/simple_enemy_projectile_batch.gd` — 同上；**顺带补上 player 版有的 `_proj.is_empty()` 早退分支**（避免空帧白跑两层循环）
- `managers/battle/simple_indirect_projectile_batch.gd` — 同上（5 个 wt）

**风险**：极低。`_apply_hit` 回调链只清 `_proj`，不触碰 buckets，成员复用安全。

---

### 优化 2：受击 `_play_hit_flash` / `_play_hit_shake` 改手写计时动画
**问题**：每次 take_damage 创建 2 个 Tween（hit_flash + hit_shake）。密集交火时（一帧几十次命中）= 每帧几十 Tween 对象分配。项目已有 v7.3 把 damage_number_display 从 Tween 改手写的成功先例。

**改法**（照搬项目已有范例）：
- flash（modulate 颜色衰减）→ 照搬 `unit_hp_bar.gd` 的 `_damage_flash` 倒计时 + lerp 模式
- shake（scale 缩放抖动）→ 照搬 `damage_number_display.gd` 的 `_pop_age` 正计时 + 分段插值模式
- 触发时只设几个 float 成员变量，不再 `create_tween`

**涉及文件**（2 个单位文件）：
- `scenes/units/construct_unit.gd`
  - 删 `_hit_flash_tween`/`_hit_shake_tween` 成员（L127-128），加 `_hit_flash_t`/`_hit_shake_t`/`_hit_flash_base_modulate` + 两个 const DURATION
  - `_play_hit_flash`(L443-452)/`_play_hit_shake`(L496-507) 重写为 `_trigger_*`（仅设状态变量，瞬间染色 + 重置 scale）
  - `_physics_process` 加一行 `_update_hit_animations(delta)` 调用
  - take_damage 调用点（L1131-1132）改调 `_trigger_*`
  - 新增 `_update_hit_animations(delta)`：flash 线性 lerp 回原色；shake 按 0.03s 分段插值 0.85→1.05→0.95→1.0
  - flash 颜色保留 RED(我方)/WHITE(敌方) 差异
  - `is_preview_mode` 早退保留
- `scenes/units/enemy_unit.gd`
  - 对称改动（成员 L110-111，触发 L1034-1057，调用 L1017-1018）
  - flash 始终 WHITE（保持现状）
  - 无 preview 早退

**风险点（已有对策）**：
- ⚠️ **scale 累积漂移 bug**（enemy_unit L1046-1048 注释记录的历史教训）→ 每次 `_trigger_hit_shake` 必须 `scale = Vector2.ONE` 重置基准，收尾段精确回 1.0
- ⚠️ **modulate 冲突**（faction_glow/phantom_clone/death_fadeout 也写 modulate）→ flash 用 `_hit_flash_base_modulate` 快照当前色作终点；连续命中时保留旧 base（不让中间色截断）；take_damage 在 `hp<=0` 后 return，与死亡淡出无时序冲突
- ⚠️ **暂停行为**：手写走 `_physics_process`，暂停时被跳过——符合预期（战斗反馈无需暂停时播放）

### 优化 3：VFX ring 每帧顶点重建 → 预分配原地复用
**问题**：`vfx_impact_factory.gd` 的 `_configure_ring_polygon`（L436-445）每次调用 `new PackedVector2Array()` + 48 次 append。tween_method 每帧回调一次，80 个 ring 激活时每帧 80×48 = 3840 个 Vector2 分配——**最强 per-frame GC 源**。

**改法**（方案 C，最小侵入）：给每个 ring 节点绑定一个预分配的 48 元素 PackedVector2Array，预计算单位圆坐标，每帧只做"单位圆坐标 × radius"原地缩放（不 new、不 append）。仍保留 Polygon2D + tween_method 驱动结构（改动最小，只优化最热的分配点）。

**具体实现**：
- `_acquire_ring`（L402-418）：新建 Polygon2D 时，给它挂一个预分配的 `_unit_points`（48 个单位圆点）+ `_scratch_points`（48 元素工作数组），存到 ring 的 meta 或用静态 Dictionary 缓存 `ring → {unit_points, scratch_points}`
- `_configure_ring_polygon`（L436-445）重写：从 ring 取出预分配数组，`for i in 48: scratch[i] = unit_points[i] * radius`（原地改，零分配），最后 `ring.polygon = scratch_points`（这一步引擎拷贝无法避免，但 buffer 不再 realloc）
- `_release_ring`（L421-432）：归还时无需清数组（下次 acquire 重写）

**涉及文件**（1 个）：
- `scripts/battle/vfx_impact_factory.gd` — `_acquire_ring` 加预分配 + `_configure_ring_polygon` 重写

**收益**：每帧每 ring 从"1 个 PackedVector2Array new + 48 Vector2 + 48 append + buffer realloc"降到"48 次原地乘法"。最坏情况 80 ring 零堆分配（引擎侧 polygon 拷贝是值语义，不计入 GC）。

**风险**：低-中。Polygon2D.polygon 赋值仍触发一次引擎侧拷贝（Polygon2D 固有行为，无法消除），但消除了所有 GDScript 侧堆分配。需确认 meta/Dictionary 缓存 ring→数组的取存开销低于原分配开销（预分配数组是必然更优）。

**备选**（如方案 C 收益不足）：方案 A 新建 RingVfx extends Node2D + _draw，彻底零分配——但改动更大、需处理空心环绘制（draw_polyline 两圈）。先做方案 C 验证，不足再升级。

## 不做的事（明确排除）
- ❌ 不动 `_proj` 的两指针压实移除逻辑（已是 O(n) 最优）
- ❌ 不动 `_apply_hit` 命中结算（P2，本次范围外）
- ❌ 不动 Line2D/炮口火/crit sparks 池化（P1，本次范围外）
- ❌ 不动启动性能 / autoload 迁移（独立方向）
- ❌ 不启用 battle_performance_monitor（独立方向）

## 验证方式
1. `Godot --headless --check-only` 通过（无语法错误）
2. 每个改动点 Grep 核对调用链一致（触发/更新/释放配对）
3. 视觉手感需游戏内实机确认（hit_flash 颜色/shake 抖动节拍/ring 扩散效果与原版一致）

## 改动量
3 类优化 × 共 6 个文件，每文件改动 6~40 行。全部向后兼容，无数据/存档/接口变更。

## 执行顺序
优化 1（批处理，3 文件，最低风险）→ 优化 2（hit 动画，2 文件，中等风险）→ 优化 3（VFX ring，1 文件）。每完成一类先停一下让你确认，再继续下一类。
