# 修复「我方战力面板 vs 上场不一致」+ 敌方战力显示口径澄清

## 问题诊断回顾

两个问题，根因不同：

**① 敌方相位师「总战力 3 万」vs 战场 6 个单位各 1 万+（合计 6 万+）**
- **这是设计口径，不是 bug**。评估值（`MasterPowerEvaluator.evaluate`）算的是"相位师裸装 6 张卡 + 相位师固有加成（属性/符文/相位仪/tier）"，**故意不含** wave/level/pressure/faction_buff 关卡难度链（`master_platform_power.gd:28-31` 注释明说）。
- 战场单位额外叠加关卡难度（`enemy_stat_resolver.resolve_classic_enemy` 的 dmg_mul_chain/hp_mul_chain 末尾乘 wave×level×pressure×faction_buff），所以实战值必然 > 评估值。
- 你已选「保持裸装固有口径」，**不改公式**，只做 UI 文案澄清。

**② 我方「面板 3000 vs 上场 12000」差 4 倍**
- **真正元凶是缓存陈旧**，不是 affix 武器卡漏算（查证：战斗部署链和评估链**都传空数组 `[]` 给 affix**，对称漏算，不构成差异源）。
- `PhaseInstrumentManager._cached_player_master_eval` 只在 `start_battle` 时 set 一次（`battle_manager.gd:176`），整场战斗不变。
- 但 10 类养成操作（强化/改造/进化/装卸卡/换相位仪/装卸符文/升相位场/激活势力/装词条）**全部不刷新缓存**，其中 3 个信号（`card_reinforced`/`modification_installed`/`card_evolved`）是死信号（零 emit 零 connect）。
- 面板读旧缓存 → 显示 3000；上场单位用实时 `_build_stats_cached` → 12000。

## 修复方案（分 3 部分）

### Part A：修缓存陈旧（核心修复，解决 4× 差距）

**A1. 在 `PhaseInstrumentManager` 新增统一的刷新方法**

`managers/phase_instrument_manager.gd`：
- 顶部加 `const MasterPlayerAssembler = preload("res://scripts/master_player_assembler.gd")`（已确认无循环依赖：assembler→platform_power→data/evolution，不回引）
- 在 L437 `clear_rank_cache()` 后新增方法：

```gdscript
## 重算并刷新玩家相位师战力缓存，emit 变化信号。
## 任何会改变玩家卡战力的养成操作（强化/改造/进化/装卸卡/换相位仪/装卸符文/升相位场/激活势力/装词条）
## 都应在操作成功后调用此方法，避免 UI 显示陈旧缓存。
func refresh_player_master_eval() -> void:
    var eval: Dictionary = MasterPlayerAssembler.evaluate_player_stars(self)
    _cached_player_master_eval = eval
    _cached_player_rank_stars = clampi(int(eval.get("stars", 3)), 1, 7)
    if not eval.is_empty() and SignalBus and SignalBus.has_signal("player_phase_master_power_changed"):
        var _pm_total: float = float(eval.get("total_score", 0.0))
        SignalBus.player_phase_master_power_changed.emit(
            _pm_total, _pm_total,
            int(eval.get("stars", 3)),
            str(eval.get("star_name", "")),
            int(eval.get("display_level", 15))
        )
```

**A2. 在 10 个养成操作的成功路径末尾插入 refresh 调用**

| 文件 | 函数 | 插入位置（return 之前） |
|------|------|----------------------|
| `managers/blueprint_manager.gd` | `apply_reinforcement` (~L891) | `_auto_save("reinforcement")` 之后、`return result` 之前 |
| `managers/blueprint_manager.gd` | `install_modification` (~L999) | `_auto_save("modification")` 之后、`return result` 之前 |
| `managers/evolution/card_evolution_manager.gd` | `evolve_blueprint` 两条路径 (~L256, ~L315) | `emit_signal("fragments_changed")` 之后、`return` 之前 |
| `managers/phase_instrument_manager.gd` | `equip_card` | 成功分支末尾（已有 `_emit_slots_changed()`，紧随其后） |
| `managers/phase_instrument_manager.gd` | `unequip_card` | 同上 |
| `managers/phase_instrument_manager.gd` | `equip_instrument` (~L1118) | `_emit_slots_changed()` 之后 |
| `managers/phase_instrument_manager.gd` | `equip_rune` / `unequip_rune` (~L1488/1513) | `_mark_rune_bonus_dirty()` 之后（自身方法，直接调 `refresh_player_master_eval()`） |
| `managers/phase_instrument_manager.gd` | `grant_phase_field_xp` (~L226) | `phase_field_level_up.emit(...)` 之后 |
| `managers/affix_manager.gd` | `_add_affix` / `reroll_affix` / `batch_reroll_affixes` | 成功分支末尾，通过 autoload 取 PhaseInstrumentManager 调 refresh |
| `managers/faction_system_manager.gd` | `unlock_faction_skill` (~L829) | `faction_skill_unlocked.emit(...)` 之后；另需在 `set_active_faction` 末尾补一次（激活切换当前无信号） |

> 实现约定：`blueprint_manager` / `affix_manager` / `faction_system_manager` / `card_evolution_manager` 通过 `Engine.get_main_loop().root.get_node_or_null("PhaseInstrumentManager")` 取 autoload 节点，`has_method("refresh_player_master_eval")` 守卫后调用。`phase_instrument_manager` 自身方法直接 `refresh_player_master_eval()`。

**A3. 性能考量**
- `evaluate_player_stars` 会对每张绿槽卡跑完整 7 层加成链（`compute_player_card_power`），玩家通常装 6 张卡，单次评估约几毫秒。养成操作是低频用户交互（点击强化/改造按钮），非每帧调用，可接受。
- 若担心高频路径（如批量改造），可后续加 dirty 标记 + 延迟刷新，但当前直接同步刷新即可，最简单可靠。

### Part C：敌方战力 UI 文案澄清（不改公式）

用户已确认敌方保持「裸装固有口径」。为避免玩家困惑（看 30000 总战力但战场 60000+），在 UI 显示处加注释性文案：

**C1. `scenes/ui/card_info_panel.gd` 两处显示点**
- `_show_enemy_phase_driver` (~L1369)：`"总战力：%d"` 改为 `"相位师本体战力：%d（不含本关难度加成）"`
- `_show_enemy_phase_master_unit` (~L1704-1705)：同样加括号注释

> 注：文案改不改你可以现场定。我倾向保留「总战力：XXXX」主标签（简短），在下方加一行灰色小字「（相位师固有战力，战场单位会叠加关卡难度）」。

## 不做的事（明确边界）

1. **不改 affix 武器卡传空数组** —— 战斗部署链和评估链对称漏算，不构成差异源。且 PhaseInstrumentManager 根本没有「战斗卡↔武器卡」装备关系（`get_loadouts()` 的 weapons 字段恒为 `[]`），修 affix 需要先建武器卡装备系统，工作量大且超出本次范围。
2. **不改敌方评估公式** —— 用户选「保持裸装口径」，30000 vs 60000 是设计意图。
3. **不激活 3 个死信号（card_reinforced/modification_installed/card_evolved）** —— 复用已有 `fragments_changed`（30+ 订阅者）更省事，且 refresh 直接在操作末尾同步调用，不需要信号中转。
4. **不加 dirty 标记 + 延迟刷新** —— 养成操作低频，同步刷新最简单可靠。

3. 开 `DEBUG_PLAYER_POWER_LOG` + `DEBUG_DEPLOY_POWER_LOG`，对比同一张卡在评估端和上场端的 stats 分量，确认 4× 差距消失（或残留差异源被定位）。
4. Grep 静态核对：确认 10 个养成操作都接入了 `refresh_player_master_eval()`，无遗漏。
