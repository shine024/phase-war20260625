# 修复：战斗胜利前卡顿（延迟掉落生成到下一帧）

## 根因
胜利判定 `_process → _check_win_lose → end_battle(true)` 全部在「最后一个敌人死亡的那一帧」同步执行。该帧堆叠三段重活：
1. **`generate_battle_completion_drops`**：遍历所有击败敌人做情报/掉落掷骰（最重）
2. **`clear_all_units`**：queue_free 全部单位
3. **`battle_ended` 信号 18 个监听者**同步挤同帧（GameManager/SaveManager/Quest/Faction/Achievement/8个UI...）

下一帧 `show_battle_result` 已是 deferred（v7.x 历史修复），所以面板本身不是主因，卡顿在第①②段。用户反馈"所有关卡都卡差不多"，说明固定开销（18 监听者）也重，需真正分帧。

## 依赖链正确性（已核实）
| 依赖 | 结论 |
|---|---|
| `_defeated_enemies` | 只在 `start_battle` 清空，end_battle 不碰 → 延迟安全 ✓ |
| spawn_system 5 个 getter（wave_total/interval/max_deployed/units_lost/wave_index） | 全部读**整场累计变量**，`clear_all_units` 不触碰 → 延迟安全 ✓ |
| `_battle_elapsed_time` | `battle_active=false` 后 `_process` 首行 return，不再增长 → 安全 ✓ |
| 重入守卫 | `end_battle` 首行 `battle_active=false`，所有入口（_check_win_lose/_on_phase_driver_destroyed/_force_defeat）都有 `if not battle_active: return` → 延迟期间不会重入 ✓ |
| ⚠️ **`_is_phase_master_battle`** | `generate_battle_completion_drops` 内部依赖它**未清零**来屏蔽相位师战改造蓝图双爆（battle_damage_system.gd L405-407 注释明示）→ **其清理必须延迟到掉落生成之后**，否则双爆回归 |

## 改动方案（单文件，集中在 `managers/battle/battle_manager.gd` 的 `end_battle`）

把 `end_battle(player_won)` 拆成「本帧轻量收尾」+「下一帧重活 finalize」两段：

### 本帧（立即执行，让胜利画面瞬间干净）
保留现有 L284-339 中所有**轻量/必要**的操作：
- `battle_active = false`（重入守卫，必须本帧）
- 清 target cache / CombatFeedback reset / PhaseInstrumentAbilities reset / rank cache 清理
- `_cleanup_spatial_grid` / 4 个 projectile batch 清理
- 停止并 `queue_free` 敌方相位驱动器
- `clear_preview_units` / `energy_manager.end_battle`
- `clear_all_units`（queue_free 帧末才真正释放，不阻塞）
- `PerformanceMetrics.end_battle_sampling` / `BlueprintManager.flush_deferred_unlock_notifications`
- `_force_defeat = false` / `_force_defeat_timer = 0.0`（兜底重置，无下游依赖）

本帧末尾：`call_deferred("_deferred_end_battle_finalize", player_won)`

### 下一帧（新增 `_deferred_end_battle_finalize(player_won)`，执行重活）
按序执行原 L315-353 的重负载部分：
1. **掉落生成**：`if player_won: _damage_system.try_grant_battle_affixes(...)` + `generate_battle_completion_drops(...)`（依赖 `_is_phase_master_battle` 仍未清零）
2. **quest notify**：`notify_battle_result(...)`（读 `_battle_result.victory_stars`，必须在掉落生成之后）
3. **清理相位师战斗状态**：`_phase_master_config = {}` / `_is_phase_master_battle = false`（必须在掉落生成之后，理由见上表）
4. **emit 信号**：`SignalBus.battle_ended.emit(player_won)`（18 监听者本帧跑，但已是胜利后第二帧，玩家已看到清场画面）

> 原来的 `call_deferred("_emit_battle_ended")` 两层延迟合并成一层——finalize 内直接 emit 即可，无需再套 deferred。

## 效果
- **本帧**：只剩轻量收尾（清缓存+queue_free），渲染线程能立即画出"敌人倒下、战场清空"的胜利瞬间
- **下一帧**：算掉落 + quest notify + emit（18 监听者）——玩家无感知，因为画面已经是胜利状态
- **再下一帧**：`show_battle_result`（已有 deferred）弹结算面板

三段重活从「挤同一帧」变成「分散到 3 帧」，且每帧之间都有渲染机会，消除卡顿。

## 不改的东西
- 不合并 `_roll_intel_item_drops` 与 `generate_battle_intel_harvest` 的两次遍历（用户本轮没选，且延迟后已不是瓶颈，留作后续可选优化）
- 不动 18 个监听者本身（延迟 emit 已让其整体错峰，无需逐个改）
- 不动 `_defeated_enemies`/spawn_system getter 逻辑（已确认延迟安全）
- 不动 SaveManager（已有 0.2s 延迟）、show_battle_result（已 deferred）

## 验证
- `Godot --headless --check-only` 通过（无语法错误）
- 静态核对：`_deferred_end_battle_finalize` 方法名调用/定义配对；`_is_phase_master_battle` 清理位置在掉落生成之后
- 实机：进任一关卡打到最后一个敌人，观察胜利瞬间是否还卡（应明显改善）；相位师战验证改造蓝图不双爆（掉落数量正常）
- 回归：AFK 挂机模式（_on_battle_ended 里 return_to_prep 依赖 emit，延迟一帧无功能影响）、必败战倒计时（end_battle(false) 走同一 finalize 路径）
