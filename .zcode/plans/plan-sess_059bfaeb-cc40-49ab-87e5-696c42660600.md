# 启动性能优化方案：轻量化 + autoload 延迟化

基于对 42 autoload 启动链路、DefaultCards 构建、ManagerLazyLoader 基础设施、SaveManager 存档路径的完整核查。

---

## 阶段三：轻量化修复（消除启动期 133 张卡的构建）

### 3.1 DefaultCards.get_all_blueprint_ids 绕过完整卡构建

**根因**：`data/default_cards.gd:159` 的 `get_all_blueprint_ids()` 调 `_ensure_card_cache()`（:161）构建全部 133 张完整 CardResource（每张 ~20 字段 + 派生计算），但调用方 `BlueprintManager._unlock_default_blueprints`（blueprint_manager.gd:171）只用 `.card_id` 字符串做集合判断。

**改动**：
- `data/default_cards.gd` 新增 `static func get_all_blueprint_ids_lightweight() -> Array`——直接从 `UnifiedCardTable.get_player_card_entries()` 取 `card_id` 字符串（战斗卡）+ 势力专属卡 ID（从 `EC.EXCLUSIVE_CARDS` 取 id）+ `EnemyBlueprints.get_all_enemy_blueprint_ids()`，**不构建任何 CardResource**
- `managers/blueprint_manager.gd:171` 改调轻量版
- 其他 `get_all_blueprint_ids()` 调用点（card_collection:105、card_enhancement:410）保持原版（它们在 deferred_init/UI 操作时调用，不在启动链路，且可能需要完整卡对象）

**注意**：`get_all_blueprint_ids_lightweight` 内部调 `EnemyBlueprints.get_all_enemy_blueprint_ids()`，后者也有同款问题（见 3.2），需一并修。

### 3.2 EnemyBlueprints.get_all_enemy_blueprint_ids 轻量化

**根因**：`data/enemy_blueprints.gd:167` 每次调 `_create_all()`（:219）构建完整卡列表只为取 card_id。

**改动**：
- `data/enemy_blueprints.gd` 新增 `static func get_all_enemy_blueprint_ids_fast() -> Array`——从 `_create_all()` 的数据源直接提取 id（需核查 _create_all 内部结构，看能否从原始数据表取 id 而不构建 CardResource）
- 若 `_create_all` 是硬编码 `_p(...)` 调用列表（无独立 id 表），则给 `_create_all` 加结果缓存（static var，首次构建后复用），避免重复构建

### 3.3 PhaseInstrumentManager 消除 _rebuild_rune_slots 重复调用

**根因**：`_rebuild_slots`（phase_instrument_manager.gd:459）在 :468（rune 分支）调一次 `_rebuild_rune_slots()`，函数末尾 :480 又无条件调一次。加上 `_ready`（:189）单独调一次——启动时共 3 次。

**改动**：
- `managers/phase_instrument_manager.gd:480` 删除函数末尾的冗余 `_rebuild_rune_slots()` 调用（rune 分支 :468 已覆盖）
- `:189` 的 `_ready` 末尾调用保留（首次初始化需要），但此时 `_rebuild_slots` 内部已调过，:189 可移除或保留作防御。核查后决定。

## 阶段四：autoload 延迟化（15 个 → lazy）

基于核查结论：**基础设施已就绪**（ManagerLazyLoader 配置完整、SaveManager `_safe_load_manager` 有 lazy-fallback）。分批执行，从零风险开始。

### 数据安全保障（前置，必须先做）

**风险**：`save_manager._collect_manager_state`（:573）和 `_collect_noncritical_save_data`（:578）用 `get_node_or_null`，延迟化的 manager 若未实例化会**漏存字段**（数据丢失）。

**修复**：给 `_collect_manager_state` 加 lazy-fallback（与 `_safe_load_manager:1351` 对称）——节点不存在时经 ManagerLazyLoader 实例化。同理 `_reset_manager_by_name`（:607）也可加（新游戏重置时确保节点存在）。

这样延迟化的 manager 在存档/读档/新游戏时会被自动拉起，数据安全。

### 第一批：零风险（5 个）

从 `project.godot [autoload]` 删除，ManagerLazyLoader 配置已就绪：
- **CharacterManager** — 0 处运行时访问，纯存档字段
- **ChallengeModeManager** — 仅 main.gd 死检查
- **LeaderboardManager** — game_manager:557 已有 ensure_loaded 守卫
- **StoryManager** — 访问全在战后回调/用户操作
- **CardCollectionManager** — 访问全在 UI 面板/信号回调

### 第二批：低风险（7 个）

需为少量直接访问点补 ensure_loaded 守卫：
- **LoreManager**、**StatBoostManager**、**AchievementManager**、**DailyTaskManager** — 补 UI 面板 + new_systems_integration 的访问点
- **IntelDiscoveryManager**、**IntelEvolutionManager**、**EnemyOriginModManager** — 情报系统，需处理 _ready 信号连接软依赖（改为 deferred 重连或 ensure_loaded）

### 不延迟的（风险高/收益低）

- **AuraManager** — `construct_unit.gd:222` 无 lazy fallback，延迟会致光环全失效
- **AffixManager**、**FactionSystemManager**、**InstanceRegistry**、**DayClock** — 访问频繁或存档强依赖
- **QuestManager**、**LevelProgressManager**、**CardEnhancementManager**、**IntelItemBag**、**IntelManual** — 访问点过多（11-18处），收益/风险比低，留待后续
- 15 个核心（SignalBus/SaveManager/GameManager 等）— 启动必需

## 验证方式

1. **Godot headless `--check-only`**：确认无语法错误
2. **Grep 静态核对**：
   - 启动链路无残留完整卡构建（get_all_blueprint_ids 不在 _ready 路径）
   - _collect_manager_state 有 lazy-fallback
   - 删除的 autoload 在 project.godot 无残留
3. **访问点守卫核对**：第二批每个延迟 manager 的直接访问点都有 ensure_loaded 或 lazy-fallback 兜底
4. **存档完整性**：延迟化的 manager 在 _collect_noncritical_save_data 经 lazy-fallback 确保不漏存

## 预期效果

- **启动**：消除 133 张卡实例化 + ~12 个非核心 manager 的 _ready（第一批5个+第二批7个），标题画面显示前的 _ready 数量显著下降
- **轻量化**：get_all_blueprint_ids 从"构建133卡"降为"O(133)字符串提取"
- **数据安全**：lazy-fallback 保证存档/读档/新游戏不丢数据
